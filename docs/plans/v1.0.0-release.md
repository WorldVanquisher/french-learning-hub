## 1. What "publish" means

**Published:**
- an annotated Git tag `v1.0.0` on the release commit;
- a GitHub Release for that tag, with `docs/releases/v1.0.0.md` as its notes.

**Not published:**
- **No image.** There is no registry. Each install builds the image locally
  from the tag.
- **The AWS public demo is not deployed** and stays frozen.

**No CI runs on the tag.** None of the three workflows triggers on tags or
releases:
- `ci.yml` (`CI`: jobs `ci`, `qdrant-integration`, `web`) runs on every pull
  request and on every push to `main`;
- `packaged-browser.yml` (*Packaged browser smoke*: job `packaged-browser`) and
  `public-demo.yml` (*Public demo*) run on pull requests and pushes to `main`
  that touch their path filters, or by hand (`workflow_dispatch`).

CI evidence must therefore come from the release commit on `main` (§5). A
documentation-only release commit matches neither path filter, so the
packaged-browser run on it has to be dispatched by hand.

## 5. Pin and verify the release commit

```bash
cd ~/workspace/flh-nas-claude          # or a fresh clone
git switch main
git pull --ff-only
git status --short                     # expect no output (remove the stray `final` file first if present)
RELEASE_SHA=$(git rev-parse HEAD); echo "$RELEASE_SHA"
git tag --list 'v1.0.0'                # expect no output: the tag must not exist yet

# CI on exactly this commit: expect "completed success" for CI and, if listed,
# Packaged browser smoke / Public demo
gh run list --commit "$RELEASE_SHA" --limit 20 --json workflowName,status,conclusion,url \
  --jq '.[] | "\(.workflowName)\t\(.status)\t\(.conclusion)\t\(.url)"'

# Packaged browser smoke runs on a push to main only when its paths changed.
# If it is not listed above for $RELEASE_SHA:
gh workflow run packaged-browser.yml --ref main
gh run list --workflow packaged-browser.yml --branch main --limit 1 \
  --json headSha,status,conclusion,url --jq '.[] | "\(.headSha)\t\(.status)\t\(.conclusion)\t\(.url)"'
#   wait until it completes, and check that headSha == $RELEASE_SHA and conclusion == success

# Local release check on the same commit (web/node_modules from the lockfile)
(cd web && npm ci)
make verify
```

## 6. Tag and publish

The release is first created as a **draft**, so you can read it on GitHub
before anyone else sees it.

```bash
NOTES=docs/releases/v1.0.0.md
grep -n 'TODO' "$NOTES"                # expect no output

git tag -a v1.0.0 "$RELEASE_SHA" -m "French Learning Hub v1.0.0"
git show --no-patch --format='%H %s' 'v1.0.0^{commit}'    # must print $RELEASE_SHA
git push origin refs/tags/v1.0.0

gh release create v1.0.0 --verify-tag --draft \
  --title "French Learning Hub v1.0.0" --notes-file "$NOTES"
gh release view v1.0.0 --web           # review the draft
gh release edit v1.0.0 --draft=false --latest   # publish
gh release view v1.0.0 --json tagName,isDraft,url
```

## 7. Upgrade the daily NAS instance to v1.0.0

This is [DAILY_USE.md](../DAILY_USE.md) §6 *Upgrade*, plus two records for
rollback. Run it on the NAS, in the checkout the daily instance is built from.

> **Caution: `~/workspace/flh-nas-claude` is also an agent working tree.**
> DAILY_USE.md uses this path, but agents work in it too. Before the
> `git switch` below, make sure no agent task is active there and that it has
> no uncommitted work. Alternatively, run the upgrade from a dedicated clone at
> the tag. The wrapper always targets the same daily Compose project and
> settings file, whichever checkout runs it.

```bash
cd ~/workspace/flh-nas-claude
bash scripts/daily/flh-daily.sh backup                    # NOTE the printed backup directory
docker image inspect --format '{{.Id}}' french-learning-hub:local   # NOTE the pre-upgrade image ID
docker image tag french-learning-hub:local french-learning-hub:before-upgrade
git switch --detach v1.0.0                                # your Git step: the checkout at the tag
bash scripts/daily/flh-daily.sh check
bash scripts/daily/flh-daily.sh up                        # rebuilds from v1.0.0, waits until healthy
curl -fsS http://127.0.0.1:8080/readyz; echo
docker image tag french-learning-hub:local french-learning-hub:v1.0.0   # keep this build addressable
```

Use your `FLH_HOST_PORT` instead of `8080`. Then run the full health check in
[v1.0.0-install.md](../releases/v1.0.0-install.md). Expect migrations
`001`–`013`, integrity `ok` and the v1.0 bundle. Finally, do one real record →
Concept round trip, or the G4 walkthrough if it has not been done yet.

## 8. Rollback

### 8a. Daily instance: the upgrade failed or misbehaves

This is the order rehearsed in
[V1-RELEASE-REHEARSAL.md](../validation/V1-RELEASE-REHEARSAL.md) §2 and
documented in DAILY_USE.md §6 *Roll back a failed upgrade*.

```bash
cd ~/workspace/flh-nas-claude
bash scripts/daily/flh-daily.sh stop                                           # 1. stop the failed service
docker image tag french-learning-hub:before-upgrade french-learning-hub:local  # 2. the known-good image
bash scripts/daily/flh-daily.sh restore <FLH_DATA_DIR>.backups/flh-<time of the backup from §7>   # 3.
curl -fsS http://127.0.0.1:8080/readyz; echo                                   # 4.
docker image inspect --format '{{.Id}}' french-learning-hub:local              # must equal the pre-upgrade ID from §7
git switch -                           # your Git step: back to the previous checkout BEFORE any later `up`
```

- **Data written after the backup is not carried back.** It stays in
  `<FLH_DATA_DIR>.before-restore-<time>`. Do not delete that directory.
- **No `before-upgrade` tag?** In step 2, check out the previous version and
  run `docker compose build app` instead (DAILY_USE.md §6).
- **Never start an older image on a newer database.** v1.0.0 adds no migration
  over the tested baseline, but this rule still applies.

### 8b. The publication itself is wrong

**If only the notes are wrong,** fix them in place:

```bash
gh release edit v1.0.0 --notes-file "$NOTES"
```

**To withdraw the release but keep the tag,** turn it back into a draft:

```bash
gh release edit v1.0.0 --draft=true
```

**To remove the release and the tag entirely.** Only do this if nobody has
consumed the tag. Otherwise, prefer publishing `v1.0.1`:

```bash
gh release delete v1.0.0 --yes --cleanup-tag   # deletes the release and the remote tag
git tag -d v1.0.0                              # local tag
git ls-remote --tags origin v1.0.0             # expect no output
```
